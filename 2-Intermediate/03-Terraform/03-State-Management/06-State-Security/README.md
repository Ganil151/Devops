# State Security

The Terraform state file is a sensitive asset that must be protected, as it contains cleartext values of everything in your infrastructure.

## Why is it Sensitive?
- **Passwords**: Database passwords, initial admin keys.
- **TLS/Certs**: Private keys and certificates.
- **Environment Metadata**: IP addresses, network topology, and account IDs.
- **Sensitive Inputs**: Variables marked as `sensitive = true` are still stored in plain text in the state file.

## Security Controls

### 1. Encryption at Rest
Always use backends that support server-side encryption (SSE).
- **AWS S3**: Enable Default Encryption and bucket policies for TLS only.
- **KMS**: Use a Customer Managed Key (CMK) for the highest level of control.

### 2. Access Control (Least Privilege)
Restrict who can access the state bucket.
- Only the **CI/CD Service Account** and a few **Senior SREs** should have read/write access.
- Use IAM Policies to block all other users.

### 3. Encryption in Transit
Ensure all communication with the backend is over HTTPS. Use `enforce_tls = true` in S3 buckets.

---

## 🏗️ Real-Life Scenario: The Log Leak
**Problem**: An organization correctly masks secrets in the CLI output using `sensitive = true`. However, an attacker gains read access to the S3 bucket where the state is stored.
**Outcome**: The attacker pulls the `terraform.tfstate` file, opens it in a text editor, and finds the database password in plain text.
**Lesson**: Marking a variable as `sensitive` protects the **Console Output**, but NOT the **State File**. The real protection is **Bucket Access Control**.

## ❓ Interview Questions
1.  **Is the state file encrypted by Terraform natively?**
    *   *Answer*: No, Terraform relies on the backend (S3, GCS, Azure) to handle encryption at rest.
2.  **How do you protect secrets from being visible in the state file?**
    *   *Answer*: You can't completely hide them from the state if they are managed by Terraform. The best practice is to store as little sensitive data as possible in Terraform (e.g., use an RDS password generated by a random resource and stored in Secrets Manager).
